## Del 1 — Syfte och scope

### NULÄGE / scope

Session 26 bär **Fas 6c — Registrations + Väntelista** (byggplan §4 Fas 6-tabellen).
Föregående session (25) stängde Inc 4 (kall /arch-audit mot Fas 6a, ren) + Fas 6b
(Events-domän: get-event + get-attendance, väg D mot T15) och lämnade 6c-stubbarna
på plats. 6c bygger ut anmälnings-domänen:

**(a) Vyer.** `/event/$eventId/anmalda` (Anmälda per event) + `/mer/vantelista`
(Väntelista). Vyerna renderar mot live-data per DoD 11/10/10.

**(b) `create-registration` Edge Function (write, idempotent).** Deployas med
idempotency-nyckel-strategi per **ADR-014** (client-genererad UUID via
`useCreateRegistration`-mutation, INVARIANT-check 400 vid saknad nyckel, lagring av
nyckel med TTL). Adresserar dubblettbuggen i `data-model.md §F.4`. Idempotency-
lagringens väg (Airtable-tabell skapad i 6c vs Fas B) avgörs av Del C-utredningen
nedan (Marcus-kvittens krävs — STOPPA-grind C1).

**(c) `get-waitlist` Edge Function (read).** Läser den egna `Väntelista`-tabellen
(`tbl2VxMx7JMkIxD4Q`), filtrerad per event + aktiv (ej "Flyttad till anmälan").

**(d) `get-registrations`-fix (T15).** Den deployade get-registrations bär den
latenta länk-ID-filter-klassbuggen (T15): `buildLinkedRecordFilter('Event', eventId)`
matchar länkens primär-display, ej record-ID → matchar ALDRIG mot skarp länk-data.
Smäller i 6c:s "Anmälda per event". Fixas per fix-mall — se STOPPA-grind B1.

Per-operations-kontrakt (ärvt): varje EF-deploy följer en namngiven UI-konsument
(M4); varje write-operation registreras i `field-allowlists.ts` med 1 deny + 1
allow-test; vy-Playwright-baseline + axe-core 0 violations. 6c ärver Fas 6a/6b:s
mönster: single-record-EF + 404-mall, `_shared/coerce.ts`, list-paginering via
`fetchAirtablePage`, cursor-conformance-test, **conformance mot SKARP datakälla**
(L154 — syntax-grön ≠ semantik-korrekt), record-ID-batch-mall (väg D) från
get-attendance/get-person, mutation-mall (ADR-016). Arv: ADR-016/026/049/050/055 +
T14 + T15.
