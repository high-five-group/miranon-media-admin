## Del 2 — Strategi-alternativ (kopierat från K2.5-utredning)

Marcus beslutar i Session 6.6.5 K1 mellan följande alternativ. Mina rekommendationer från K2.5-utredningen bevaras nedan; bekräftas eller revideras vid 6.6.5-start.

### A — Acceptera + manuell merge

Marcus mergar Dependabot-PR:er manuellt efter `gh pr checkout <nr>` + lokal verifiering (`npm install && npm run test:api && npm run build`).

**Fördel:** Bevarar maximalt skydd mot secrets-läckage; ingen ny attack-yta.
**Nackdel:** Dependabot-PR:er har permanent röd CI-status; måste mergas via "merge without checks"-bypass i Settings; Marcus-manuell-arbete varje vecka.

### B — Konfigurera Dependabot-specifika secrets

Settings → Secrets and variables → Dependabot → lägg samma 6 `TEST_*`-secrets där. GitHub injicerar då i Dependabot-PR:er automatiskt.

**Fördel:** CI grön på Dependabot-PR:er; samma test-coverage som main-branch.
**Nackdel:** Dependabot-bot får read-access till staging-secrets. Acceptabelt om dependabot-config kan låsa till verified-actions (vilket vi gör per ADR-029 § Third-party Actions-policy).

### C — Skip staging-tests för Dependabot-PR:er

Lägg if-villkor på `API tests (staging)`-steg + `E2E tests (staging)`-steg i `ci.yml`:
```yaml
if: github.actor != 'dependabot[bot]'
```

**Fördel:** Enklast att implementera; ingen secrets-exponering; Dependabot-PR:er CI grön.
**Nackdel:** Staging-tests körs inte för dependency-bumps → mindre verifiering. Marcus måste manuellt verifiera staging-impact innan merge.

### D — Hybrid (skip staging + e2e, behåll resten)

Skip endast `API tests (staging)` + `E2E tests (staging)` för Dependabot. Behåll `test:api:pure` + `typecheck` + `biome` + `build` + `lint` + `actionlint` + `yamllint` + `lychee` (alla nya grindvakter från Session 6.6).

**Fördel:** Fångar ~80 % regressionsrisk (pure-tests + typecheck + build) utan secrets-exponering; bästa kost/nytta-balans.
**Nackdel:** Staging + e2e-test-coverage gap för dependency-bumps. Mitigation: Marcus manuell staging-verify innan merge för icke-trivial-bumps.

### Min preferens-ranking (från K2.5)

**D > B > C > A.** Hybrid D är bästa kost/nytta. B är näst bäst om secrets-zoning anses säkert nog. C är enklast men tappar mest staging-skydd. A kräver Marcus-manuell-arbete varje vecka.

### Eventuellt nya alternativ post-6.6

Reserveras för utforskning vid 6.6.5-start om Marcus eller Code identifierar fler tekniska lösningar (t.ex. environment-based deployment, conditional secret-mounting via reusable workflow, etc.).
